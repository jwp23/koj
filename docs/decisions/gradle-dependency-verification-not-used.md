# Gradle Dependency Verification Not Used

Decision: The project does not use Gradle's dependency verification (`gradle/verification-metadata.xml`).
Build-tooling artifacts (Gradle plugins, the Android Gradle Plugin's lint and test tooling) are
protected by the controls already in place: the Dependabot cooldown, version pins, strict lockfiles
audited by osv-scanner for the shipped classpaths, and the checksum-pinned Gradle wrapper
(`distributionSha256Sum`). Compatibility between Kotlin, Gradle, and the Android Gradle Plugin is a
separate concern, handled by [build-toolchain-versions.md](build-toolchain-versions.md).

Rationale: Gradle's documentation says generating the file "trusts whatever is currently in your
repositories", so a checksum only detects different bytes published under a version already
recorded. It does not detect a malicious new release, which is the likelier threat, and which the
cooldown is there to catch. The file must be regenerated on every dependency change, and Dependabot
cannot do that. Regenerating it automatically on Dependabot pull requests would stamp each new
release with its own checksum, so the check would verify nothing; doing it in CI needs either a
write-privileged token or `pull_request_target` running pull request code, which GitHub's secure-use
guidance warns against; and a push with the default token does not re-run CI. Regenerating it by hand
leaves hundreds of entries that Gradle marks `origin="Generated by Gradle"` (unreviewed) and that
nobody can realistically check against a second source.

What was tried (2026-11-14): `./gradlew --write-verification-metadata sha256` over the CI task set
produced 477 components and 810 entries. Strict verification passed the full build, and a wrong
checksum, or a missing entry, failed it, including for the Kotlin Gradle plugin. The Dependency
Submission workflow would also need the graph plugin it injects to be trusted in the file, which
the `gradle/actions` documentation says requires signature verification or an explicit trust entry;
that could not be tested outside a push to `main`.

Revisit if the project gains contributors or distributes to enough users that a tampered build
plugin would matter more, or if Dependabot gains support for updating the file.
